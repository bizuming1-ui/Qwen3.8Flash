# 设计决策记录（自问自答）

> 需求原文里的关键要求：**「一模一样」的界面、扫码多端、不用手动刷新、每种语言都用上、确认后现在清零且当前生产数显示该数字、精准开发。**
> 下面是我在动手前对自己提出的问题，以及最终选定的答案。每一条都对应到代码里的具体位置。

---

### Q1 `确认` 之后，`当前生产数` 到底是「覆盖」还是「累加」？
**A：累加。** 需求原句是「当前生产数那里要显示刚刚现在那里的数字」，但 `当前生产数` 在语义上是
「本单已生产的累计件数」，而 `现在` 是「这一次的件数」。采用覆盖会让累计值倒退，属于数据事故。
因此定为：`当前生产数 += n`、`生产总数`不变、`现在 = 0`，在内核里是一个原子操作
（`core/engine.c` 的 `CONFIRM` 分支）。用户在提问环节也确认了「累加」。

### Q2 `生产总数` 是手填还是系统统计？
**A：手工设定，且确认不碰它。**（第二轮需求修正）它代表订单的目标总量/计划数，由人填写；
`确认` 只做一件事：`当前生产数 += 现在`、`现在 = 0`。C 内核提供 `SET total`，
但 `CONFIRM` 分支完全不动 `total` —— 两者职责彻底分开，互不干扰。

### Q2.5 为什么手机扫码会 403，怎样解决？
**A：** Arena 私有预览由平台网关限制，二维码的普通浏览器请求未必有访问令牌。应用不能伪造该令牌。线上改用 GitHub Pages 作为公开网页、Supabase 作为共享后端，二维码指向 Pages；本机预览如需与手机同步，可配置 `CLOUD_BOARD_URL` 连接同一云端。两套后端的数据不会自动合并。Supabase 默认域名不支持直接提供 HTML 页面，因此不能声称整个网页都托管在 Supabase。

### Q3 两个人同时按「确认」会不会算错？
**A：不会。** 所有写请求都汇聚到 C 内核这一个串行点。Node 侧不计算、不缓存待写值，只转发。
两次确认在内核队列里依次执行，`current` 各加自己的 `n`、`total` 不变，`rev` 各加 1，广播按 `rev` 顺序下发。

### Q4 「现在」是新输入的值，如果客户端防抖还没推上去就按了确认，怎么办？
**A：确认消息自带金额。** `CONFIRM <n>` 里的 `n` 直接取自输入框当前内容，内核以它为准，
不依赖此前是否同步过 `now`。这样「输入 → 立刻按确认」不会因为 80ms 防抖而丢数。

### Q5 「现在」清零后，别的设备上正在输入「现在」的人会不会被吞掉？
**A：会清零，这是业务本意。** 确认是全局事务，所有设备的 `现在` 都应该归零，
所以 `commit` 帧对数字字段使用「强制回填」，覆盖本地聚焦状态；而 `生产单/产品` 的文本字段
在用户正在输入时不会被远端覆盖（1.2s 抑制窗口），避免打字被打断。

### Q6 为什么不用轮询（setInterval 拉接口）？「刷新率要快」怎么保证？
**A：WebSocket 长连接推送。** 轮询的最低延迟等于轮询间隔，且连接数一多就打爆服务端。
现在是「谁改了立刻推给所有连接」，本机实测内核往返 0.1ms，端到端通常 <20ms；
另外 20s 一次 ping/pong 心跳探活，45s 无 pong 判定僵死并自动重连。

### Q7 断线、切后台、换网络之后需要用户按刷新吗？
**A：不需要。** 前端指数退避自动重连（200ms → 3s 封顶），`onopen` 立刻发 `sync` 拉最新快照；
`visibilitychange` 回到前台也再对齐一次。所有下行帧带单调 `rev`，客户端丢弃过期帧，
所以「重连后看到的永远是最新值」。

### Q7.5 如果用户的网络/公司代理把 WebSocket 掐掉了怎么办？
**A：降级而不是报错。** `send()` 在 WS 不可用时自动改走 `POST /api/set` / `POST /api/confirm`，
同时前端启动 1s 一次的 `/api/state` 轮询；WS 恢复后立刻停掉轮询回到推送模式。
写路径仍然经过同一个 C 内核，所以两种通道的语义完全一致，不会出现"两条路算出来的数不一样"。

### Q8 状态放在哪里？Node 内存里行不行？
**A：不行。** Node 单进程内存会被重启清零，多实例时还会各说各话。
本地模式的状态由 C 内核管理，变更写入 C++ 日志服务，重启时回放；云端模式则由 Supabase PostgreSQL 的事务和持久存储负责。
实测：填好数据 → `Ctrl+C` → `npm start`，`rev/total/current/生产单/产品` 全部还原。

### Q9 日志坏了怎么办？（断电导致半行、磁盘写坏）
**A：每行带 CRC32 校验和**（`#<crc>#<json>`）。回放时校验失败的行直接跳过，用「最后一条完好记录」
恢复；Python 统计侧同样逐行校验并统计损坏行数（`/api/stats` 的 `corrupt_lines`）。
文本字段在日志里用 base64 存储，天然免转义，C/C++/Python 三边都不会因为引号、换行、中文而解析出错。

### Q10 为什么二维码不是写死的网址？
**A：因为地址因环境而异。** 服务端读 `x-forwarded-proto` / `x-forwarded-host`（沙盒预览代理会带），
拼出当前公网地址再生成 SVG；如果检测到是 `localhost`，自动替换成局域网 IP，手机同 WiFi 也能扫。
二维码本身由 `qrcode` 包在服务端渲染成 SVG，前端只放 `<img>`，省掉前端打包体积。

### Q11 界面要不要为了"好看"改一点（加阴影、加状态灯、加连接提示）？
**A：首屏一律不加。** 需求是「和照片一模一样」。唯一的视觉变化是**离线时确认按钮变半透明**
（否则用户会以为点了没反应），以及输入框获得焦点时一圈 3px 的极淡描边（否则不知道在哪个框里打字）。
两处都在非正常态才出现。

### Q12 原图标签后面的 `↵` 要不要画出来？
**A：默认不画，可开关。** 那是 Word 的段落编辑标记，不是设计意图。用 `?marks=1` 可完整复刻截图。

### Q13 字体怎么保证像？
**A：宋体字族栈** `Songti SC → STSong → NSimSun → SimSun → Noto Serif CJK SC`，`font-weight:700`，
标签 26px、输入 30px、按钮 30px（均按原图字面高度 22px  Ink 反推）。

### Q14 手机屏幕放不下 1356×834 怎么办？
**A：桌面保留等比缩放，竖屏手机重排。** 桌面继续使用 `scale = min(vw/1356, vh/834)`；竖屏手机使用可滚动的单列布局和至少 44px 的触控高度，避免输入框缩得无法操作。

### Q15 大写数字、负数、前导零、粘贴一堆字符，内核会不会崩？
**A：三层校验。** 前端只允许数字、去前导零、限 13 位；网关再做 `Math.trunc` + 范围裁剪；
C 内核用独立的 `parse_u64`（拒绝非数字、超过 15 位、超过 1e12 的值），文本字段过滤控制字符并按
UTF-8 边界截断到 200 字节。任何一层的非法输入都返回 `ERR`，状态不会被污染。

### Q16 「每种语言都用上」——Go / Rust / Java 也要塞进去吗？
**A：不塞。** 沙盒只放行 npm / PyPI / GitHub 三个域名，Go 的 `go.dev`、Rust 的 `static.rust-lang.org`、
Java 的 Adoptium CDN 都不可达，装不上工具链；硬塞会破坏"一条命令启动"。
最终采用 C（状态）、C++（持久化）、Python（统计）、TypeScript（网关+前端）四语言分工，
进程间用 Unix Domain Socket + 行协议解耦，将来加 Go/Rust 只需再注册一个进程。

### Q17 为什么 C 内核不直接说 JSON？
**A：为了不写 JSON 解析器。** 服务间用「空格分隔 + 文本字段 base64」的行协议：
C 侧零依赖、不会因为转义出错；C++ 侧负责把 KV 组装成 JSON 落盘；Python 侧负责 JSON 解析。
每一层都只做自己最省事、最稳的那部分。

### Q18 怎么证明它是真的能跑，而不是"看起来能跑"？
**A：`npm test` 使用隔离临时目录和随机端口，覆盖只读、管理员权限、超额不变、并发、双端广播、审计、重启恢复。** `npm run smoke` 可检查正在运行的自托管服务，但会修改目标看板，需配置本地管理员密码。

### Q19 出事了我怎么自查？
**A：`/debug.html`。** 一屏看到：三个子服务的 PID 与存活、内核往返延迟、在线设备数、当前 `rev`、
累计产量、确认次数、每分钟节拍、损坏日志行数、最近 20 条确认明细，并能一键导出 CSV / 清空数据。

### Q20 一个进程崩溃了整个看板会不会挂？
**A：不会全挂。** `server/src/supervisor.ts` 监督三个子进程，异常退出后 300ms→5s 退避重启；
C 内核与日志服务各自会重连对端并补写快照；网关对内核的请求有 5s 超时，不会把请求堆死。

### Q21 超过总数时可以截断到上限吗？
**A：不能。** 确认必须全部成功或全部拒绝。C 内核和 PostgreSQL 事务均在修改前检查，拒绝时返回 `EXCEEDS_TOTAL`，不改变数量或版本，界面显示错误并保留输入。

### Q22 管理员是否可以将总数改到当前数以下？
**A：不能。** 管理员可设置总数、清空看板及修改分享地址，但不能突破 `当前生产数 <= 生产总数`。云端额外使用数据库 CHECK 兜底；本地 C 内核也独立校验。`当前生产数` 对所有身份和所有公开写入接口只读。

### Q23 云端如何处理两个设备同时确认？
**A：** PostgreSQL 事务锁定同一状态行后检查剩余额度，超额请求拒绝；请求 UUID 去重避免同一个请求重复累计。Realtime 推送与两秒轮询同时使用，避免断线后依赖手动刷新。

### Q24 管理员凭据和公开二维码如何隔离？
**A：** 用户指定 Supabase Auth 身份；只保存授权的用户 ID，不保存或展示密码。扫码地址和 publishable key 不含 service-role key。普通看板操作目前允许知道公开地址的人进行，管理员操作则在数据库内校验身份；如需限制普通用户访问，需要另行设计登录权限。
